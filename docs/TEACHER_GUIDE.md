# Concurrency Theatre: руководство для занятия

Дата редакции: **2026-10-24**. Архивная основа: `SkyProse/ParallelProgrammingTex`, commit `1c53d6eb08a7d0041a6f54728b6ba90a59507454`, 19 февраля 2020 года. Авторы исходного пособия: Соснин В. В., Балакшин П. В., Шилко Д. С.; Университет ИТМО. Новые сцены являются отдельной учебной адаптацией. Оригинальные файлы `listings/` сохранены.

## Что должен унести студент

Цель занятия — объяснить причину наблюдаемого результата и назвать границу вывода. Просмотр анимации и получение правильного ответа по знакомому рисунку сами по себе не доказывают понимания.

Для каждой сцены используйте один цикл:

1. Сформулировать контракт: что именно программа должна делать.
2. Зафиксировать прогноз до запуска.
3. Получить трассу модели или настоящий результат измерения.
4. Указать событие, правило или границу таймера, которые объясняют результат.
5. Решить новую задачу переноса без подсказки исходного рисунка.

В интерфейсе есть **challenge** и отдельный **transfer**. Можно работать в парах: один участник предлагает объяснение, второй ищет допустимый контрпример. Скорость реакции не оценивается. Режимы текста и двумерного представления подходят для того же занятия, что и пространственная сцена.

Полный материал удобнее разделить на два занятия по 45–60 минут. На первом разобрать корректность и размещение данных; на втором — очередь, GPU и методику измерения. Это предложение по организации, а не измеренная длительность прохождения или исследование эффективности обучения.

## Перед началом

- Уточните, что **шаг модели не равен миллисекунде**. Меняющийся темп воспроизведения не ускоряет исследуемую программу.
- Покажите три происхождения данных: модель, измерение этой сессии, импорт. У импорта остаются среда и методика исходного запуска.
- Проверьте доступность WebGPU перед GPU-частью. Если адаптер недоступен, отсутствие результата обсуждается честно; учебный текст и остальные модели остаются полезны.
- Для измерений закройте ненужную нагрузку и зафиксируйте режим питания. Приостановка рендера уменьшает вмешательство приложения, но не превращает ноутбук в изолированный стенд.
- Откройте панель источников. Дайте студентам увидеть разницу между архивным листингом и проверенной адаптацией.

## 1. Развилка времени

**Контракт:** оба потока выполняют свою работу и освобождают блокировки. Модель содержит два потока, две обычные блокировки и одну итерацию, по пять успешных инструкций на поток.

Попросите сначала получить тупик: T0 берёт A, T1 берёт B. Следующие инструкции обоих потоков недоступны. Событие «ожидал 10 мс» не нужно. Затем вернитесь к первому выбору и получите завершение того же кода. Последним действием поменяйте порядок захвата в T1 на A → B.

Обсудите три разных утверждения:

- «Эта трасса завершилась» — свидетельство одного запуска.
- «В этой конечной модели найден тупик» — контрпример корректности её программы.
- «В этой конечной модели тупиков не найдено полным перебором» — результат только для объявленного пространства состояний.

Не переносите последний вывод на дополнительные блокировки, повторяющиеся циклы, внешние ресурсы или иной код. Удачное расписание и исправление программы — разные вмешательства.

**Ключ challenge:** общий порядок A → B. **Ключ transfer:** долгая пауза сама по себе не доказывает deadlock. Попросите ученика назвать владельца ресурса и доступный следующий шаг, а не просто произнести слово «цикл».

## 2. Контракт гонки

В сцене разыгрываются два увеличения общего значения, изначально равного нулю. Это последовательная согласованная учебная модель отдельных чтений, локальных вычислений и записей. Она не исполняет `raceConditionalExample1.cpp` и не перечисляет допустимые исходы C++ data race.

Получите потерянное обновление: оба потока читают 0, оба локально вычисляют 1, обе записи оставляют общий результат 1. Сравните с атомарным режимом, где два изменения дают 2. Затем покажите снимок: оба локальных результата равны 1, общая переменная остаётся 0.

Архивная пара примеров особенно полезна для вопроса о требованиях. `old_a` сохраняется до параллельной области; его печать сообщает исходное состояние. Это подходит для отчёта об исходном состоянии, но не заменяет синхронизированное наблюдение последующего изменения.

**Ключ challenge:** атомарное увеличение, если общий результат обязан быть 2. **Ключ transfer:** неизменяемый снимок, если обе независимые работы должны использовать исходную версию. Неверный вывод, который нужно поймать: «раз запись стала локальной, программа исправлена при любом требовании».

Подробное основание различия модели и C++: [рабочий проект стандарта, intro.races](https://eel.is/c++draft/intro.races).

## 3. Микроскоп памяти

Поля `a` и `b` занимают по одному байту в модели. Один поток работает с `a[i]`, другой — с `b[i]`. Сначала оставьте AoS, затем сравните с SoA, где начало второго массива выровнено по границе линии, и с отдельным выровненным слотом для каждого скаляра.

Попросите предсказать, какие обращения затронут чужую копию той же линии. Следите за **рисунком обращений**, а не только за названием размещения. SoA помогает именно при данном разделении полей; два потока, обрабатывающие соседние элементы одного массива, могут столкнуться с другой формой false sharing.

Обязательно сравните занимаемую память. В режиме padded шаг размещения — округлённый вверх до линии максимум размера линии и `padding + 1` байт. Нулевой дополнительный padding всё равно означает отдельный минимальный слот размером в линию. Это не вычисленная стоимость промаха кеша.

Счётчики имеют узкий смысл: инвалидации — удалённые копии, лишившиеся актуальности; передачи — обращения, требующие взаимодействия с чужим владельцем или копией; true/false sharing различают затронутые скаляры. Это не PMU, не полная реализация MESI и не реальное время. Только совместные чтения не дают harmful false sharing; хотя бы одна сторона должна писать. См. [документацию Linux](https://www.kernel.org/doc/html/latest/kernel-hacking/false-sharing.html).

**Ключ challenge:** SoA с выравниванием при разделении по полям. **Ключ transfer:** padding не устраняет true sharing одного значения. Вопрос синхронизации такого значения решается отдельно.

## 4. Эстафета CAS

Сначала найдите единственное событие, которое действительно привязывает новый узел: успешный strong CAS `next`, меняющий null на адрес узла. Это точка линеаризации добавления в этой модели. Потом намеренно оставьте `tail` позади и предложите второму потоку помочь.

Покажите значения `actual`, `expected` и `desired` отдельно. При провале сравнения `expected` получает наблюдённое значение; успешный CAS не заменяет его на `desired`. Включая спонтанную неудачу, подчеркните: она разрешена только для **weak шага помощи tail**. Сильная вставка не получает случайный отказ от переключателя.

Модель содержит только добавление двух уникальных узлов к фиктивному начальному узлу. В ней нет dequeue, повторного использования адреса, освобождения памяти и доказательства всех C++ memory orders. Нельзя делать вывод «мы получили промышленную lock-free очередь». Определение CAS: [рабочий проект C++](https://eel.is/c++draft/atomics.types.generic).

**Ключ challenge:** после успешного `next` узел уже связан, даже если хвост продвинет помощник. **Ключ transfer:** weak CAS может спонтанно не пройти; предусмотренный алгоритмом повтор не означает повреждение очереди.

## 5. Ткацкий станок GPU

Различайте глобальный индекс вызова, локальный индекс, рабочую группу и optional подгруппу. Запуск WGSL возвращает значения этих идентификаторов там, где функция поддержана. Диаграмма группирует данные; она не записывает временное расписание физического GPU.

Предложите группе из 64 логических вызовов найти объяснение без слов «обязательно два warp по 32». При наличии `subgroups` исследуйте наблюдённый размер и lane ID. Для subgroup ID и явного размера подгруппы существуют отдельные условия доступности. Если функция отсутствует, запишите «недоступно»; не рисуйте ожидаемый ответ как полученный с устройства.

**Ключ challenge:** workgroupSize задаёт логическую рабочую группу. **Ключ transfer:** для 130 элементов при 64 вызовах нужны три группы; 62 лишних индекса не должны обращаться к массиву. Для алгоритмов с барьером необходимо соблюдать требования участия WGSL, а не бездумно вставлять ранний выход перед барьером.

Референс: [WGSL, редакция 21 октября 2026](https://www.w3.org/TR/2026/CRD-WGSL-20261021/).

## 6. Обсерватория ускорения

Эта часть продолжает существующую лабораторную № 4. Используется один `u32-mix-reduce-v1`: детерминированный вход xorshift32, преобразование по глобальному индексу, сумма по модулю 2³². На каждом холодном и тёплом запуске проверяются все выходные элементы и сумма. Контрольная сумма в отчёте не заменяет поэлементную проверку.

Рекомендуемый порядок:

1. Зафиксировать устройство, браузер, backend, размер входа и число исполнителей.
2. Проверить правильность результата.
3. Раздельно сохранить холодный запуск и тёплую серию. По умолчанию серия содержит семь наблюдений; интерфейс и API ограничивают объём эксперимента.
4. Прочитать `timingScope`: браузер считает end-to-end время, включая применимые выделения выходов, сообщения Workers или GPU upload/dispatch/readback. Проверка правильности выполняется вне этой границы.
5. Сравнить сырые наблюдения, медиану, среднее, разброс и интервал. Отметить возможный тренд, нагрев и зависимость соседних измерений.

Интервал использует Student t для среднего и выборочное стандартное отклонение с делителем `n − 1`. Уровень 95% описывает покрытие процедуры при повторении исследований с подходящими предпосылками. Он не означает вероятность 95% для уже вычисленного фиксированного интервала. Перекрытие двух интервалов не является самостоятельным тестом равенства; см. [NIST](https://www.itl.nist.gov/div898/handbook/eda/section3/eda352.htm).

GPU timestamp pass, если доступен, — отдельная величина. Нативный OpenMP runner из `native/` запускается другим процессом и измеряет compute-only с предварительно выделенными массивами. Импортировать эти данные полезно, напрямую делить их на браузерное end-to-end время — методологически неверно.

**Ключ challenge:** выровнять задачу, проверку и границу времени до расчёта ускорения. **Ключ transfer:** исследовать разброс и методику, не объявляя универсального победителя по одному размеру или перекрывающимся интервалам.

## Что принимать в отчёте

Короткий отчёт должен содержать контракт, происхождение данных, условия модели или эксперимента, свидетельство, причинное объяснение и границу вывода. Для опыта — также сырые samples, cold/warm, `timingScope`, проверку выходов и среду. Для модели — расписание, выбранный режим и точку изменения.

При оценивании различайте воспроизведение известного сценария, самостоятельное причинное объяснение и перенос на новую задачу. Прогресс в браузере хранит факт прохождения взаимодействий; он не является сертификатом знаний. Для исследования эффективности курса понадобится отдельный дизайн с новыми заданиями и участниками.

Не снижайте оценку за выбор текста вместо 3D, отключённое движение или отсутствие optional GPU-возможности. Содержательный критерий — сохранённая причинная аргументация.
